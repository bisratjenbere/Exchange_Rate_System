# ADR-006: Source Taxonomy, Adapter Families, and Observation Model

Date: 2026-10-10
Status: PROPOSED — for owner review before M2 schema is frozen

---

## 1. The fundamental observation model

Every bank, regardless of source type, produces the same logical unit:

> **One observation = one currency × one category × one effective period × one source**

The adapter's only job is to extract that unit from whatever shape the source uses.
The pipeline's job is to receive that unit in a normalized contract and handle everything else.

This means the adapter output contract is fixed and source-independent:

```
AdapterRecord:
  source_currency_code   str          # exactly as the source wrote it
  currency_name          str | None
  category               str          # 'cash' | 'transactional' | 'weighted_average' | 'indicative_reference' | UNKNOWN
  buying_rate            Decimal | None
  selling_rate           Decimal | None
  source_rate_text       str | None   # original string before parsing
  effective_date         date | None
  effective_date_basis   str          # 'source_published' | 'source_inferred' | 'collection_date_fallback' | 'unknown'
  source_record_key      str | None   # stable ID from source, if any
  source_publication_key str | None   # stable publication/snapshot ID, if any
  quote_currency_code    str | None   # TO VERIFY per source
  unit_multiplier        int          # default 1
  raw_excerpt            dict | None  # source record's own JSON/text, size-limited
  mapping_notes          list[str]    # any flags, warnings, or ambiguities
```

The pipeline receives a list of AdapterRecords and never knows which bank produced them.

## 2. Source type taxonomy (all 32 banks classified)

### Type A — Publication-per-date JSON API
One API call returns one or more publication records. Each record has an explicit effective date and contains a list of currency rates. The API supports date filtering.

**Pattern:** `GET /api?Date=YYYY-MM-DD` → array of publication objects, each with nested rate array.

**Banks:** CBE

**Structural signature:**
- Outer array: one element per publication date
- Each element: publication ID + date field + nested rates array
- Each rate item: currency code/name + category-named rate fields (cashBuying, transactionalBuying…)
- Zero values mean "not offered" (confirmed by cross-category pattern)
- Stable publication ID (MongoDB ObjectID) usable as source_publication_key
- Stable per-currency ID usable as source_record_key

**Identity strength:** STRONG — stable IDs + explicit date → identity_status = confirmed

**Adapter strategy:** One fetch per date. Explode nested rates into one AdapterRecord per currency × category pair. Map zero → None.

---

### Type B — Flat currency-row JSON API (latest only)
One API call returns the current rates as a flat array. One row per currency. No publication history. Effective date may be per-row or absent.

**Sub-type B1 — Explicit effective_date per row (Rammis):**
- Envelope: `{ base_currency, effective_date, rates: [...] }`
- Each rate: `{ id, currency, effective_date, buying, selling }`
- base_currency = ETB confirmed
- Per-row effective_date (rows updated independently)
- Single buying/selling pair — category unresolved (TO VERIFY)
- Stable integer `id` per currency row (TO VERIFY across fetches)

**Sub-type B2 — Wide row, all categories in one record (Addis):**
- Envelope: flat array, no wrapper
- Each row: `{ id, currency, buying, selling, transactionBuying, transactionSelling, weightedBuying, weightedSelling, createdAt, updatedAt }`
- No effective_date field — updatedAt is the only candidate (TO VERIFY)
- Zero string "0.0000" and null both appear — semantics unverified
- id is a row number, not a publication ID
- Currently returning 403

**Banks:** Rammis (B1), Addis (B2)

**Identity strength B1:** MEDIUM — stable id + per-row date → identity_status = derived (date not independently confirmed)
**Identity strength B2:** WEAK — no publication date, no stable publication ID → identity_status = ambiguous

**Adapter strategy:** One fetch. For B1: one AdapterRecord per row (one category). For B2: explode each wide row into up to 3 AdapterRecords (plain, transaction, weighted) — skip plain pair until category confirmed.

---

### Type C — CMS/Framework JSON API
A CMS (Strapi, custom) exposes a structured API with pagination, nested attributes, and framework-specific envelope.

**Sub-type C1 — Strapi v4 (Wegagen):**
- Envelope: `{ data: [...], meta: { pagination } }`
- Each item: `{ id, attributes: { date, code, unit, buying, selling, tra_buying, tra_selling, ... } }`
- Explicit `date` per record (rows updated independently)
- `unit` field present (= 1 for all observed records)
- `buying`/`tra_buying` identical in fixture — category ambiguity (TO VERIFY)
- Stable Strapi integer `id` per currency row

**Banks:** Wegagen (C1). Potentially others in later waves.

**Identity strength:** MEDIUM — stable id + explicit date → identity_status = derived

**Adapter strategy:** One fetch. Unwrap Strapi envelope. One AdapterRecord per row per category pair. Handle pagination (currently total=10, fits in one page).

---

### Type D — Multi-table static HTML (separate tables per category)
A static HTML page with 2–3 `<table>` elements, each representing one category. Tables are independent and may have different effective dates.

**Pattern:** `soup.find_all("table")` → [transactional_table, cash_table, weighted_avg_table] or similar ordering.

**Banks:** Dashen, Omo, Tsehay (partial), NIB (partial)

**Structural signature:**
- Table count: 2–3
- Each table has a category-identifying header (column header text or preceding heading)
- Date may be embedded in column header (Dashen weighted avg: "Weighted Average Rate on October 09, 2026"; Omo: "07/10/2026" in header cell)
- "No Trade" / "-" = NULL
- Currency column: code only, or "CODE – Name" format

**Date availability:**
- Dashen: weighted avg has date in header; transactional/cash do not → mixed identity strength
- Omo: all three tables have date in header → strong identity
- NIB: separate date-only table (table[0]) applies to cash/txn tables → strong identity
- Tsehay: no date in any table → ambiguous

**Identity strength:** STRONG where date is in header (Omo, NIB); MIXED for Dashen; WEAK for Tsehay

**Adapter strategy:** Parse each table independently. Extract category from header text. Extract date from header cell if present. Emit one AdapterRecord per currency × category. Never apply a date from one table to another table.

---

### Type E — Wide-column static HTML (all categories in one table)
A single `<table>` with multiple buying/selling column groups, one group per category.

**Pattern:** Header row 0 = category spans (`CASH | TRANSACTION | AVERAGE`); Header row 1 = `Buying | Selling | Buying | Selling | ...`

**Banks:** Bunna, CBO (combined cash+txn table), Amhara, Hibret, BOA (sections within one table)

**Structural signature:**
- Multi-level headers: category in row 0, buying/selling in row 1
- Column index mapping: cash_buy=col2, cash_sell=col3, txn_buy=col4, txn_sell=col5, avg_buy=col6, avg_sell=col7
- Currency: name + code in same cell ("US Dollar (USD)") or separate columns
- Date: sometimes in table header (CBO: "Exchange Rate October 10, 2026"; BOA: "October 10, 2026"), sometimes absent

**Identity strength:** STRONG where date in header (CBO, BOA); WEAK where absent (Bunna, Amhara, Hibret)

**Adapter strategy:** Parse multi-level header to build column→category mapping. Emit one AdapterRecord per currency × category. Extract date from header row 0 if present.

---

### Type F — Single-table static HTML (one category, ambiguous)
A single `<table>` with one buying/selling pair. Category is not labeled in the table.

**Banks:** DBE, Siinqee, Global (table 0), Goh Betoch (plain pair)

**Structural signature:**
- Headers: `Currency | [Code] | Buying | Selling`
- No category label
- No date in table

**Identity strength:** WEAK — no date, no category label → identity_status = ambiguous, category = UNKNOWN until verified

**Adapter strategy:** Emit one AdapterRecord with category=UNKNOWN. Flag for review. Do not ingest into trusted view until category is confirmed.

---

### Type G — Text-embedded rates (no table)
Rates are embedded in page text or non-table HTML elements (divs, spans). No `<table>` element.

**Banks:** Sidama, Enat, Ahadu, Berhan

**Structural signature (Sidama):** Per-currency text blocks: "USD United States Dollar Cash Buying 161.7237 Birr Cash Selling 164.9582 Birr Transactional Buying 161.7237 Birr..."
**Structural signature (Enat):** Inline text: "USD 161.3736 164.6011 EUR 187.0333 190.7740..." with date "Oct 10, 2026" in page text
**Structural signature (Berhan):** "1 USD ($) Buying ... Selling ..."

**Identity strength:** MEDIUM for Enat (date in text); WEAK for others (no date)

**Adapter strategy:** Regex/text extraction per bank. More fragile than table parsing — schema_change detection is critical. Each bank in this group needs its own text parser.

---

### Type H — JavaScript-rendered (browser required)
Rates are loaded via JavaScript after page load. Static HTML fetch returns empty tables or placeholder values ("--", "...").

**Banks:** Zemen (AJAX with "--" placeholders), Tsedey (empty table rows), Gadaa (no data), Anbesa (JS), Shabelle (JS), and partially Enat/Ahadu

**Sub-type H1 — Known AJAX endpoint (Zemen, Oromia, Awash):**
Rates loaded via a POST AJAX call. Endpoint identifiable from browser dev tools.

**Sub-type H2 — Pure JS rendering (Tsedey, Gadaa, Anbesa, Shabelle):**
No known endpoint. Requires headless browser (Playwright/Selenium).

**Identity strength:** Unknown until rendered

**Adapter strategy:** H1: identify AJAX endpoint from official page at runtime, POST with nonce. H2: headless browser. Both deferred to later waves. Not available in current environment.

---

### Type I — Blocked / Unresolved
Source returns 403, has SSL errors, or has no reachable domain.

**403 (programmatic block):** Siket, ZamZam, Abay, Addis API
**SSL cert error:** Hibret, Amhara, BOA (data accessible with verify=False)
**DNS failure:** Hijra
**Official source unresolved:** (Anbesa and Shabelle now have official sites — moved to Type H)

## 4. Cross-cutting observations

### 4.1 "Not offered" sentinel values
Every source uses a different sentinel for a rate side that is not offered:
- CBE, Addis: numeric `0` or string `"0.0000"`
- NIB, Omo, Tsehay, Amhara, Global, CBO: string `"No Trade"` / `"NO TRADE"`
- Goh Betoch, Dashen: no zeros observed yet
- Rammis, Wegagen: no zeros observed yet

**Rule:** The adapter normalizes all sentinels to `None` before emitting the AdapterRecord. The pipeline never sees a sentinel — it only sees `Decimal | None`. The original source text is preserved in `source_rate_text`.

### 4.2 Currency identification patterns
Sources use four different currency identification patterns:

| Pattern | Example | Banks |
|---------|---------|-------|
| ISO code only | `"USD"` | CBE, Rammis, Wegagen, Dashen, NIB, Tsehay, Siinqee, Global |
| Name + code in parens | `"US Dollar (USD)"` | Amhara, Berhan |
| Code + dash + name | `"USD – US Dollar"` | Omo |
| Name + code separate columns | `"US Dollar" / "USD"` | Bunna, Tsehay (weighted), DBE |
| Name only | `"US Dollar"` | Global, Siinqee (some) |

**Rule:** The adapter always emits both `source_currency_code` (the raw code string) and `currency_name` (the raw name string). The pipeline maps to canonical `currency_code` only when the mapping is verified. Never infer a code from a name alone.

### 4.3 Effective date patterns
Five distinct date patterns across sources:

| Pattern | Format | Banks |
|---------|--------|-------|
| API field YYYY-MM-DD | `"2026-10-10"` | CBE (Date), Rammis (effective_date), Wegagen (date) |
| Table header — month name | `"October 10, 2026"` | BOA, NIB (Oct 10, 2026), Enat (Oct 10, 2026) |
| Table header — month name (in column) | `"Weighted Average Rate on October 09, 2026"` | Dashen weighted |
| Table header — DD/MM/YYYY | `"07/10/2026"` | Omo |
| Table header — combined | `"Exchange RateOctober 10, 2026"` | CBO |
| None | — | Bunna, Goh Betoch, Tsehay, Hibret, Amhara, Siinqee, DBE, Global, Sidama, Ahadu, Berhan |

**Rule:** One tested `parse_effective_date(text, hint_format)` function handles all formats. Returns `(date, basis)` where basis is `source_published` when parsed from source text, `collection_date_fallback` when absent. Fallback dates never participate in identity.

### 4.4 Category identification patterns

| Pattern | Banks |
|---------|-------|
| Named API fields (cashBuying, transactionalBuying…) | CBE |
| Wide row, all categories (buying, transactionBuying, weightedBuying) | Addis |
| Single pair, category in API field name (tra_buying) | Wegagen |
| Separate tables, category in table header text | Dashen, Omo, NIB, Tsehay |
| Wide table, category in column group header | Bunna, CBO, Amhara, Hibret, BOA |
| Single table, no category label | DBE, Siinqee, Global, Goh Betoch |
| Text blocks with category labels | Sidama, Enat |
| Single pair, category unknown | Rammis, Siinqee, Global |

**Rule:** When category cannot be determined from the source, emit `category = UNKNOWN`. Never guess. The pipeline routes UNKNOWN to the review queue and excludes from trusted view.

### 4.5 "No Trade" / zero / null unification
All three mean the same thing: this rate side is not offered by this bank for this currency/category on this date. The adapter maps all three to `None`. The pipeline stores `NULL` in the database. The original source text is preserved in `source_rate_text`.

### 4.6 Identity strength and trusted view eligibility

| Identity strength | Condition | Trusted view eligible |
|------------------|-----------|----------------------|
| STRONG | Stable source ID + source_published date | Yes, after validation |
| MEDIUM | Source_published date, no stable ID | Yes, after validation (derived key) |
| WEAK | No source_published date (fallback only) | No — identity_status = ambiguous |
| UNKNOWN | JS-rendered, not yet fetched | No |

This means approximately 14 of 32 banks will produce ambiguous observations until either (a) a source-published date is found, or (b) the owner approves a documented source-specific fallback rule.

## 5. Shared adapter base class design

All adapters inherit from one base:

```python
class BaseAdapter:
    adapter_key: str          # matches rate_source.adapter_key
    source_url: str
    collection_method: str    # 'api' | 'html' | 'ajax_endpoint' | 'browser'

    def fetch(self, session: requests.Session) -> RawResponse:
        # polite fetch: UA, timeout, retry, rate limit
        # raises on HTTP error or timeout
        ...

    def parse(self, raw: RawResponse) -> list[AdapterRecord]:
        # bank-specific: implemented per adapter
        # must not make network calls
        # must not access clock
        ...

    def schema_fingerprint(self, raw: RawResponse) -> str:
        # deterministic hash of structural signature (not values)
        # triggers raw capture on change
        ...
```

The pipeline calls `fetch()` then `parse()`. It never calls bank-specific methods directly.

## 6. Adapter family implementations

### Family API-A (CBE)
- Fetch: `GET /cbeapi/daily-exchange-rates/?Date=YYYY-MM-DD`
- Parse: iterate `ExchangeRate` array, emit 2 records per currency (cash + transactional), map 0 → None
- Schema fingerprint: hash of top-level keys + ExchangeRate item keys

### Family API-B1 (Rammis)
- Fetch: `GET /api/v1/exchange-rates/latest?base_currency=ETB`
- Parse: iterate `rates` array, emit 1 record per currency (category TO VERIFY → UNKNOWN for now)
- Schema fingerprint: hash of rate item keys

### Family API-B2 (Addis)
- Fetch: `GET /api/exchange-rates`
- Parse: iterate array, skip ETB row (id=1), emit up to 2 records per currency (transaction + weighted), skip plain pair until category confirmed, map "0.0000" → None
- Schema fingerprint: hash of record keys

### Family API-C1 (Wegagen)
- Fetch: `GET /api/exchange-rates?populate=*`
- Parse: unwrap Strapi `data[].attributes`, emit 1 record per currency (category TO VERIFY), use `unit` field
- Schema fingerprint: hash of attributes keys

### Family HTML-D (Dashen, Omo, NIB, Tsehay)
- Fetch: `GET <url>`
- Parse: `soup.find_all("table")`, identify each table by header text, parse independently
- Date extraction: regex on header cell text per table
- Schema fingerprint: hash of (table count, per-table header texts)
- Config per bank: table index → category mapping, date format hint

### Family HTML-E (Bunna, CBO, Amhara, Hibret, BOA)
- Fetch: `GET <url>`
- Parse: find wide table, parse multi-level header to build column→category map
- Date extraction: from header row 0 text if present
- Schema fingerprint: hash of header structure
- Config per bank: column group positions, date format hint

### Family HTML-F (DBE, Siinqee, Global, Goh Betoch)
- Fetch: `GET <url>`
- Parse: find single table, emit records with category=UNKNOWN
- Schema fingerprint: hash of header texts

### Family HTML-G (Sidama, Enat, Ahadu, Berhan)
- Fetch: `GET <url>`
- Parse: regex/text extraction, bank-specific patterns
- Schema fingerprint: hash of structural markers in page text
- Note: most fragile family — schema_change detection is critical

### Family HTML-H1 (Zemen, Oromia, Awash)
- Fetch: GET official page to extract nonce, then POST AJAX endpoint
- Deferred: nonce extraction requires browser dev tools investigation

### Family HTML-H2 (Tsedey, Gadaa, Anbesa, Shabelle)
- Fetch: headless browser (Playwright)
- Deferred: no headless browser in current environment

## 7. New observation per new fetch — the key rule

Every fetch produces a new collection run. The pipeline determines whether the observations from that run are:

1. **Identical to existing** → deduplicate (no new row, no version increment)
2. **New publication** (different effective_date or publication_key) → new logical observation, version 1
3. **Changed value, same publication** → change_candidate (not automatic correction)
4. **Ambiguous identity** → stored with identity_status=ambiguous, excluded from trusted view

"New observation as new" means: every fetch that produces a record with a different (source_publication_key, currency, category) tuple — or a different value for the same tuple — is treated as a new event to be evaluated, never silently overwritten. The fingerprint determines whether it is truly new or a duplicate fetch of the same data.

This is already in the LOCKED design. What this analysis adds is the recognition that for WEAK-identity banks (no source-published date), nearly every daily fetch will produce a new ambiguous candidate because the fallback date changes. These banks will accumulate ambiguous candidates until identity is resolved. The review queue must handle this volume gracefully.

## 8. Decisions this analysis surfaces

### Decided here (within autonomy rules):
- Adapter family taxonomy (A, B1, B2, C1, D, E, F, G, H1, H2, I) — recorded above
- Shared `BaseAdapter` interface — fetch/parse/schema_fingerprint separation
- All sentinels (0, "0.0000", "No Trade", "NO TRADE", "-", "...") → None in adapter output
- Currency identification: always emit both source_currency_code and currency_name; never infer code from name
- Category=UNKNOWN for single-table no-label sources (Type F) — routes to review, excluded from trusted view
- `parse_effective_date(text, hint_format)` as a single tested function for all date formats

### Needs owner decision:
1. **WEAK-identity banks and review queue volume**: ~14 banks will produce ambiguous candidates on every daily fetch. The review queue will grow indefinitely unless either (a) a fallback rule is approved per source after verifying publication behavior, or (b) ambiguous observations are silently dropped (which weakens the LOCKED rule). Recommendation: implement a per-source `max_ambiguous_candidates` config that stops accumulating after N identical-value ambiguous records for the same currency/category, treating them as "same publication, no new information." This is not a correction — it is a deduplication rule for structurally ambiguous sources.

2. **Type F category=UNKNOWN**: For DBE, Siinqee, Global, Goh Betoch — the single buying/selling pair is almost certainly either cash or transactional. Ingesting as UNKNOWN means zero trusted-view coverage for these banks until manually reviewed. Recommendation: allow a per-source `default_category_override` config that can be set after the owner reviews the official display, without requiring a code change.

3. **SSL verify=False for Hibret, Amhara, BOA**: Acceptable for production with explicit per-source config flag `ssl_verify: false` and a recorded terms-of-use finding? Recommendation: yes, with the flag documented and the finding recorded.
